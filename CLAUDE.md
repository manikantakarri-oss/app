# CLAUDE.md

Guidance for working in this repo. `README.md` has the long-form rationale and `TESTING.md` the test notes; this file is the map of what the app does and the rules that are easy to break.

## What this is

**Agent Portal** is a friendly front door to Databricks agents for people who never open a Databricks workspace. It is a Databricks App: a FastAPI backend (`app.py` + modules) serving a statically exported Next.js UI (`web/`).

- **End users** sign in, see only the agents they may use, and chat with them.
- **Admins** (members of the workspace `admins` group) manage access, build agents, control foundation-model access, and view cost, activity and problems.

**Core principle: the portal stores nothing of its own.** Agent identity, names, capabilities, access and the LLM switch all live in Databricks-native state (serving endpoint tags and ACLs, workspace groups, system tables). Delete and rebuild the portal and no configuration is lost. Don't add a local database or config file for state. The only tables the portal writes are the optional problem log and chat history in Delta (see below).

## Deploy

`app.yaml` is the Databricks Apps manifest (runs `uvicorn app:app --port 8000`). See README "Deploy from scratch". The gotchas:

- **Scopes are not applied from `app.yaml`.** Put them on the app record (`databricks apps update agent-portal --json @update-scopes.json`) **then stop/start the app**. The runtime mints user tokens from the scopes it booted with.
- Scope names are `<api-group>.<resource>`; bare names (`genie`, `unity-catalog`, ...) are rejected. Invoking agents needs `model-serving`.
- `DATABRICKS_HOST` arrives **without a scheme** in Apps; `dbx.host()` normalises it.
- `web/` is **committed** (it is what gets deployed) and `ui/out/` is gitignored. After any UI change, rebuild and copy to `web/` or the change will not ship.
- **New client / workspace:** set `PORTAL_LOG_TABLE` in `app.yaml` to `<existing catalog>.<schema>.portal_logs` (the only per-client line). The app creates the schema (`store.ensure_schema`, best effort) and its tables on first use (`store.ensure_table`: on Azure, `CREATE TABLE IF NOT EXISTS` is refused without CREATE TABLE even when the table exists, so a refused create falls back to checking the table is readable; if it is not, the error names the GRANTs to run) and picks a warehouse itself unless `PORTAL_LOG_WAREHOUSE` pins one. The SP needs `USE CATALOG` + `CREATE SCHEMA` on the catalog (or `USE SCHEMA` + `CREATE TABLE` on an existing schema) and `CAN_USE` on a warehouse.
- **Onboarding an agent** = sharing its serving endpoint with the app's service principal (CAN_MANAGE). Until then it does not appear in the portal at all.

Environment variables (all optional): `PORTAL_LOG_TABLE`, `PORTAL_LOG_WAREHOUSE`, `PORTAL_CHAT_TABLE`, `PORTAL_CHAT_RETENTION_DAYS` (default 180), `DATABRICKS_CONFIG_PROFILE`, `DATABRICKS_WORKSPACE_ID`. `.env.local` holds local `DATABRICKS_HOST`/`DATABRICKS_TOKEN`; it is gitignored. Never print, log or commit its contents.

## Security model (do not weaken)

Two identities, used deliberately:

- **App service principal** (`dbx.app_token()`): metadata plane only. Reads endpoint ACLs, manages groups and tags, runs the Delta log/chat SQL.
- **Signed-in user's OBO token** (`X-Forwarded-Access-Token`, via `dbx.user_token()`): every agent invocation, file upload/download, and billing/audit query. Databricks then enforces endpoint ACLs and Unity Catalog itself, so a bug here can show a card but cannot widen access.

Rules:
- If no user token is forwarded in Apps, **fail closed (403)**. Never fall back to the service principal for invocation.
- `/api/chat`'s `_allowed_agent` pre-check is for clear errors only, not the security boundary.
- Admin routes go through `_require_admin` (membership in `admins`).
- Saved chats are filtered by the caller's user name taken from their token, never from a request field, and every value is a bound SQL parameter. That filter is the whole privacy boundary.
- Tokens and request bodies are never logged.
- Revoking access is a `PUT` of the surviving ACL entries and must **preserve service-principal grants**, or the portal locks itself out. Permission `PATCH` is additive.
- Local dev (no Apps runtime) uses the CLI token for both identities and the header badge says "local dev · your CLI identity".

## Features

### 1. Agent catalog and access (`access.py`)
- An agent is a serving endpoint with task `agent/*` (Responses, Chat). Endpoints tagged `portal=true` are also published. Embedding endpoints are excluded.
- Users see only agents they hold `CAN_QUERY`/`CAN_MANAGE` on (directly or via a group). `GET /api/agents`, `GET /api/session` (identity, `is_admin`, auth mode).
- Friendly names come from endpoint tags `display_name`, `blurb`; fallback is `_prettify`. Agent kinds (Multi-agent, Document expert, Agent, Chat model) are labelled for non-technical readers.
- Agent Bricks agents keep their real ACL at `/api/2.0/permissions/supervisor-agents/<agent_id>` (the `agent_id` tag), not on the endpoint. `perm_paths` handles both.

### 2. Chat (`chat.py`, `adapters.py`, `ui/components/Chat.tsx`)
- `POST /api/chat` runs under the user's token. Reply is normalised to `{reply, tools, citations, attachments}`.
- **Probe-and-learn protocol handling.** Endpoints disagree on the wire format (`input` for Responses vs `messages` for Chat/ChatCompletions). `adapters.build` dispatches on `task`; if the endpoint rejects the field (`wrong_field`), it switches once and `learn()`s the answer per endpoint. Agent Bricks serves no OpenAPI doc, so this cannot be discovered up front.
- **Shape-agnostic parsing** (`adapters.parse`): Responses `output[]`, ChatCompletions `choices[]`, ChatAgent `messages[]`, `final_response`/`result` wrappers, legacy `predictions`, `custom_outputs`, bare strings. Extracts text, tool names, citations, attachments.
- **SSE errors arrive as HTTP 200.** `chat._read` / `adapters.parse_sse` parse the stream and raise `AgentStreamError` on `event: error` (Genie-backed agents do this). Don't rely on status codes alone.
- **MCP approvals are auto-resolved.** A reply containing `mcp_approval_request` has not run the tool yet. `chat._resolve_approvals` replays the full prior turn plus `mcp_approval_response` items (the endpoint is stateless; `previous_response_id` is ignored). **Each response goes straight after its own request** (`adapters.build_approval_replay`): an assistant may ask for several tools in one reply, and requests-then-responses is answered with HTTP 200 and the message "Invalid approval response. The approval response ID does not match the request." (seen live 2026-10-08 with `get_rate_card` + `find_inventory`; interleaving runs both; one request per reply hid it). Every tool call is its own round, so `MAX_APPROVAL_ROUNDS` is 12 (a media plan takes 5+); hitting the cap appends a "stopped part-way" note, and `tools` lists every tool that ran across rounds. A long multi-tool answer can take 3-5 minutes.
- UI: markdown rendering, tool/citation display, copy, file attach, download of generated files, history panel.

### 3. Saved chat history (`chats.py`, `store.py`, `ui/components/ChatHistory.tsx`)
- Optional. Enabled by `PORTAL_CHAT_TABLE` (`catalog.schema.table`), else `portal_chats` beside `PORTAL_LOG_TABLE`; neither set = history off (`historyEnabled` false in UI).
- One append-only row per message, conversation = rows sharing a UUID, title = first question. Retention purge after `PORTAL_CHAT_RETENTION_DAYS`.
- Saved in a `BackgroundTask` after a successful reply only. Routes: `GET /api/chats`, `GET/DELETE /api/chats/{cid}`.

### 4. File-driven agents (`files.py`)
- Tag `upload_volume` (`catalog.schema.volume`) enables **Attach a file**; tag `accepts` (e.g. `xlsx, csv`) restricts types, enforced client and server. Max 100 MB.
- `POST /api/upload` writes to the UC volume **with the user's token**; the path is named in the turn so the agent reads it with its volume tool.
- Tag `output_volume` lets agents hand back generated files; `GET /api/download` is limited to paths inside that volume (`filestore.in_volume`).
- `sync_agents.py` auto-derives `upload_volume` from an agent's own `volume` tool.

### 5. Foundation models: removed
- The "General assistant" tab (raw `llm/v1/chat` foundation models, switched on by the `portal-llm-users` group, routes `/api/models` and `/api/admin/llm`) was removed. The portal only offers agents now.
- `llm.py` keeps only the billing code (`spend`, `_warehouse`, `_pretty_model`), used by Costs and the dashboards.

### 6. Manage section (admins; routes under `/api/admin/*`)
There is no tabbed "admin console" any more: each admin area is its own sidebar page, each shown once. **Insights** (`Insights` in `Dashboard.tsx`: adoption, use, real spend and cost per question per assistant, est. cost per person in the People table), **Access** (`Admin.tsx`), **Build** (`Builder.tsx`), **Monitoring** and **Audit log** (`Ops.tsx`). Old links `#admin`, `#activity` and `#health` open Access, Audit log and Monitoring (`LEGACY` in `page.tsx`). Sections live in one `SECTIONS` list in `page.tsx` that drives the sidebar, titles and quick switcher.
- **RBAC with Databricks groups**: the assistant list is fetched with the user's own token, so Databricks decides visibility, including through groups (and nested groups) created in Databricks. Two things the portal does not do for a group made in Databricks: grant it `CAN_USE` on the app itself (needed to open the portal at all; `create_group` does this for groups made in the portal), and grant UC data access.
- **Access**: `GET /api/admin/overview`; `POST /api/admin/grant` (grant/revoke a user or group per agent), `POST /api/admin/group` (create a group "agent set"; also grants it app access), `POST /api/admin/group-members` (replaces the whole membership list, no incremental add/remove), `POST /api/admin/meta` (set tags: `display_name`, `blurb`, `upload_volume`, `accepts`, `output_volume`, `portal`; empty value deletes the tag).
- If the portal only has `CAN_VIEW`/`CAN_QUERY` on an agent, the admin sees a plain-English "not shared yet" note and controls are hidden.
- **Spend** (`llm.spend`, `GET /api/admin/cost`): queries `system.billing.usage` joined to `list_prices` for MODEL_SERVING and SUPERVISOR_AGENT, run as the admin. Shown on Insights, matched to assistants by the line's `raw` endpoint name; unmatched lines are "Other spend". Degrades to "Spend unavailable" if billing is unreadable.
- **Audit log** (`events.py`, `GET /api/admin/activity`, UI `AuditLogPage` in `Ops.tsx`, tabs Portal / Databricks): one record per meaningful action (opened the portal at most once per person per 30 min, asked, uploaded, downloaded, deleted a conversation, granted/revoked, team and settings changes, created/edited/deleted an assistant). **Never what anyone typed**: a question is recorded as assistant + outcome + time taken. Recording: the access-log middleware `events.begin()`s every API request, routes `events.note(action=..., target=..., label=..., detail=...)`, the `DbxError`/`HTTPException` handlers `events.failed()` the reason, and the middleware `finish()`es with status and timing. In memory always; durable in `PORTAL_EVENTS_TABLE` or `portal_events` beside `PORTAL_LOG_TABLE` (created on first use, 180-day retention, queued and batched). The second tab, "Databricks", shows only access changes from the system audit log below (`cats=access`); deployments, sign-ins and internal checks are deliberately not offered there.
- **Monitoring** (`events.health`, `GET /api/admin/agent-health`, UI `MonitoringPage`; statuses Healthy / Degraded >=5% / Failing >=25% / Low traffic <3 questions; a refused or unknown assistant name counts as an error cause but never as an assistant row, via `detail.known`): per-assistant failure rate, average and p90 response time, last problem, with failures sorted into plain-English kinds (`events.KINDS`: no permission, data access, timed out, not ready, a tool failed, too many requests, rejected) and a fix hint for each. A reply that came back fine but contains a failed tool (`Called X -> Error calling tool ...`) counts as `tool_error`. The portal's technical log (below) is folded at the bottom. Tests: `test_events.py`.
- Both pages share one look in `Ops.tsx`: a toolbar (view on the left, the same 7/30/90 period control as Insights on the right), one `Card` per list with its filter chips in the header, one `Row` (mark, sentence, time, a tag only on failure, detail on click) and the shared `Pager`/`usePage` from `bits.tsx` (also used by the Insights and My dashboard tables) for portal actions, Databricks changes, failures and technical lines alike. Keep it lean: usage and spend belong to Insights, so these pages do not repeat them.
- **Changes in Databricks** (`audit.py`, `GET /api/admin/audit`): human sentences built from `system.access.audit` (e.g. "X gave Y permission to use Z"), with category filters and name lookups. Audit has ACL changes only; **conversations are not in it**.
- **Technical log** (`logbuf.py`, `logsink.py`, `GET /api/admin/logs`): WARNING+ log lines. In-memory ring buffer (500 lines) by default; durable Delta table when `PORTAL_LOG_TABLE` is set (queued, batched, bounded to 1000, never logs its own failures).

### 7. Assistant builder (`builder.py`, `genie.py`, `knowledge.py`, `ui/components/Builder.tsx`, `GenieBuilder.tsx`, `KnowledgeBuilder.tsx`, `BuilderParts.tsx`)
Admin-only **Create an assistant** tab. It opens on a type picker (a fourth "Describe it in your own words" beta card, section 12, appears when the designer is on; "Combine tools and information" = Supervisor Agent, "Answer questions from your documents" = Knowledge Assistant, "Answer questions from your data" = Genie space), then a step-by-step wizard. Both wizards share `BuilderParts.tsx` (step frame, access step, review section, done screen), so they look and behave identically. The Supervisor wizard has six steps (Name it, Instructions, Abilities, Files, Who can use it, Review; the access step is hidden when editing). It creates a real Agent Bricks **Supervisor Agent** (`/api/2.1/supervisor-agents`) so it also appears in Databricks.
- Tool kinds (`TOOL_TYPES`, **no cap** per assistant: Databricks documents 50 tools and agents together and its create screen stops there, but tested live 2026-10-06 the API took 123 tools, listed them all and the assistant answered; the tools list pages at 100, so always read it with `builder.list_tools`): UC function, Genie space, Knowledge Assistant, UC volume, MCP via UC connection, Databricks app (MCP), Vector Search index (**unconfirmed** shape, flagged in the UI).
- Routes: `/api/admin/builder/{types,sources,principals,agents}` plus `GET/PUT/DELETE .../agents/{id}`; `sources` browses catalogs/schemas/etc. for the pickers.
- **Identity fallback** (`builder.act`): try the admin's token first; retry as the app SP **only** when Databricks says the token lacks the `supervisor-agents` scope. Never retry other refusals. Admin is then given CAN_MANAGE; results include `acted_as`.
- Creation is all-or-nothing (a rejected tool deletes the half-built agent). Edit reconciles tools and leaves unmodelled tool types alone. Edit/delete require the admin to hold CAN_MANAGE on the agent.
- **Genie spaces** (`genie.py`, routes `/api/admin/builder/genie[/{id}]`, wizard `GenieBuilder.tsx`): choose a SQL warehouse and tables, add example questions and a note, pick who can use it, review. Stored as the `serialized_space` JSON (version 2; tables sorted by identifier, ids 32-hex). Editing round-trips the existing space and keeps everything the builder does not model (joins, SQL examples, benchmarks). Create uses the same `builder.act` fallback; **edit/delete/list use the admin's own token only, no fallback**, so Databricks decides. Sharing is CAN_RUN on `/api/2.0/permissions/genie/<id>`, applied immediately. Because the portal only chats with serving endpoints, a default-on option also creates a one-tool Supervisor Agent around the space (its access is applied by `finish_provisioning`); if that fails the space is kept and a warning says so. People also need `SELECT` on the tables, which the portal cannot grant, and the UI says so. `text_instructions` item shape is **unconfirmed** (not in the API reference's example).
- **Knowledge Assistants** (`knowledge.py`, routes `/api/admin/builder/knowledge[/{id}]`, wizard `KnowledgeBuilder.tsx`): name, description (required by Databricks), up to 10 document folders (each a UC volume path plus an optional subfolder, a name and a required "what is in it"), optional instructions, who can use it, review. Databricks only allows letters, numbers and dashes in the name, so the friendly name is stored in the endpoint's `display_name` tag and the Databricks name is derived from it (editable under Advanced). Only the "Files in a Volume" source type is offered. Create uses `builder.act` (the `knowledge-assistants` scope is expected to be refused for Apps user tokens, so the app identity usually does it) and is all-or-nothing: a rejected folder deletes the half-built assistant and the Databricks message is shown as it came. **Unconfirmed**, not in any reference this was built from: the `files.path` field carrying the volume path, the `knowledge-sources` sub-path and the `:sync` call (best effort, failure ignored). Edit changes name, description and instructions only; documents are shown read-only and changed in Databricks. Edit/delete use the admin's token with no fallback. Reading documents takes minutes, so `knowledge.finish` waits up to ~10 minutes for the endpoint, then hands over to `builder.finish_provisioning` with an **empty `agent_id`** (the supervisor-agents permission path is not a Knowledge Assistant's).
- `finish_provisioning` runs as a background task after create: waits for the endpoint (takes minutes), then tags it (name, description, `agent_id`, file tags) and shares it with the creator and portal; wizard-selected teams/people get CAN_QUERY through `access.set_grant`. If it times out, `python sync_agents.py --apply` finishes it.

- **MCP tool catalog** (`mcps.py`, `GET /api/admin/builder/mcps`, UI `McpCatalog.tsx`): the Supervisor wizard's Abilities step lists the "Tools" kept in a public GitHub repo as selectable cards (`McpPicker`): search, All/Selected/Works-with-files chips, 12 per page with the shared `Pager`, a live "N added" counter (every tool and ability; no cap), and the chosen tools listed under the grid as `ChosenRow`s (name and "when should it use this" on one line on wide screens), so ticking never reshuffles the grid. "Other abilities" uses the same card and rows. Unavailable tools (`problem`) cannot be picked; one that failed last time is tagged. **No deployment status or jargon is shown** (the audience is non-technical): the person ticks tools and the portal does the rest. Nothing is deployed from the picker. The repo is `PORTAL_MCP_REPO` (default `manikantakarri-oss/mcps`; `PORTAL_MCP_REF`, default `main`; `PORTAL_MCP_TOKEN` only for a private repo): one folder per MCP with `mcp.yaml` (the card), `app.yaml` and the server; folders starting `_` are ignored. The whole repo is read as one `codeload.github.com` tarball (no API rate limit), cached 5 minutes. **Stores nothing:** "deployed" means a Databricks App named `mcp-<folder>` exists (or the card's `app_name`); state comes from `GET /api/2.0/apps` each time. `mcps._state` trusts Databricks' status first (a RUNNING app is ready even with a pending deployment; an unrecognised status on an ACTIVE app counts as ready and is logged as `unrecognised status`), because a wrong "not ready" makes the background task wait 20 minutes and never attach the tool. Databricks keeps a just-deleted app in the list (compute `DELETING`, status still RUNNING), so `plan` also asks for the app directly before attaching it now, `DELETING` counts as not deployed, and `deploy_and_attach` waits (up to ~5 min) for the old copy to disappear before recreating it. `builder_create` plans with `derive=True` (an unflagged `app` tool whose name matches the catalog is treated as a catalog tool; edits only plan flagged tools so existing tools are never detached), logs `tool <slug>: app <name> listed as X, now Y` for every decision, and as a last resort, if Databricks answers the attach with 404 "does not exist", `mcps.defer` sets every catalog tool aside for installation and creation is retried once without them.
  - **The assistant is only created once its tools are ready.** On Create/Save the wizard (`readyTools` in `Builder.tsx`) first looks at the ticked catalog tools (`api.mcps(true)`); if any are not running it calls `POST /api/admin/builder/mcps/prepare` (`mcps.prepare` marks them "getting ready" at once and clears an old failure; `mcps.install_quietly` runs in the background), shows a status panel under the button (`ToolProgress`: each tool with where it is up to, from `state_note`, plus a timer) and polls the list every 6 s (up to 20 min). If a tool is waiting with nothing installing it (e.g. the server restarted and lost `_progress`), the loop asks `prepare` again every 30 s; leaving the wizard stops the loop. A tool that fails stops everything with a plain message and **nothing is created**; retrying installs it again. Only then does it POST the create/save, where `mcps.plan` finds every tool running and attaches it immediately. `install` creates (or switches on) the app, waits for a just-deleted one to go away (~5 min), copies the folder to `/Workspace/Shared/agent-portal-mcps/<folder>` (`workspace/import`, `format: AUTO`), **waits for the app's compute to be ACTIVE (starting it if STOPPED; up to 10 min) because Databricks refuses a deployment with `Cannot deploy app ... as it is not in RUNNING state` (seen live)**, and deploys it (`/apps/<name>/deployments`, SNAPSHOT; that exact 400 is retried a few times); `_installing` stops two requests installing the same app. The old path is kept as a safety net: if a tool is still not running at create time, the assistant is created and `mcps.deploy_and_attach` (background) installs it, grants folder access and attaches it, and the finish screen says "Getting your tools ready" (the create route also retries once without a tool Databricks says does not exist, via `mcps.defer`).
  - **Tool secrets** (`needs.secrets` on the card, e.g. `gam-key`, `gam-network`): kept per client in the secret scope `agent-portal` (`PORTAL_SECRET_SCOPE`) of the client's workspace, put there by the Portal Deployer on each deploy (`workspace.sync_tool_secrets`, from the client's encrypted GitHub env secret; the portal SP gets MANAGE on the scope). A tool whose secrets are missing is listed with a "not connected yet" `problem` and `start` refuses with 409; otherwise its app gets each secret as an app resource of the same name (added by PATCH to an app made earlier), so the value goes from Databricks to the tool, never through the portal. Names only are read (`secrets_present`, cached 60 s).
  - **Folder access is automatic** (`mcps.grant_volumes`): a new app runs as its own service principal with no access to anyone's volumes. The card's `needs.volumes` (`read`/`write`) plus the assistant's Files step (`volumes_for`: upload folder and folder tools = read, results folder = write) decide the grants: `READ_VOLUME` (and for results `READ_VOLUME` + `WRITE_VOLUME`: seen live, a Files API write with only WRITE_VOLUME is a 403) on the volume plus `USE_CATALOG`/`USE_SCHEMA`, via `PATCH /api/2.1/unity-catalog/permissions/<kind>/<name>`, as the admin (`builder.act`, so Databricks limits it to what that admin may grant). Runs inline in the create/save request (before the assistant is handed back; problems come back as `warnings`) for every running catalog tool, and in `deploy_and_attach` for a tool installed by the safety net, before attaching it. It therefore covers tools **already running** (so an existing app is topped up, not recreated; `as_catalog_tools` recognises tools already on an assistant by app name). Additive and idempotent; a refusal is logged with the exact grant to make by hand and never fails the save. **Unconfirmed:** the UC permissions call under the admin's Apps token (may fall back to the app identity, which usually cannot grant).
- The app name is **always taken from the catalog**, never from the request. Identity is `builder.act` (admin token, app identity only on a scope refusal; the admin is made manager if the app identity created the app). In-memory `_progress` only decorates the copy phase and failures. No `apps` user scope is requested (its name is unconfirmed and a bad scope name breaks the scope update).
  - **Unconfirmed, never run live:** Workspace import of plain/binary files with `format: AUTO`, the pending-deployment status values, the new app's service principal reading the source folder without a grant, and a Supervisor Agent being allowed to call the app. Volume access an MCP needs is declared in `needs.volumes` and shown; the portal does not grant it. Tests: `python test_mcps.py`. The repo's README explains how to add an MCP (`_template/`).

### 8. Dashboards (`dashboard.py`, `ui/components/Dashboard.tsx`)
**My dashboard** tab for everyone: questions asked, conversations, assistants used, files sent/received, a questions-per-day chart and most-used assistants. Admins get a **Me / Everyone** switch: a ranked table of people, any one person's numbers, and an **estimated** cost per person.
- Source is the saved-chat table only (`chats.py`), so it needs history on and covers only chats since then; with history off the API returns `enabled: false` and the UI explains instead of showing zeros. Duplicate writes are removed (`QUALIFY ROW_NUMBER`).
- **Privacy:** `GET /api/dashboard/me` takes the user from the caller's token and ignores any `user` parameter. Admin routes (`/api/admin/dashboard/{people,person,costs}`) expose **counts only**, never question text or chat titles. Keep it that way.
- **Cost per person is an estimate**, not a bill: Databricks bills per endpoint, so each endpoint's real cost (`llm.spend`, run as the admin) is split by each person's share of questions to it. Cost with no portal usage behind it is shown as "Not from the portal", never spread over people. The UI labels it "Estimate" everywhere. Don't present it as exact.
- The SQL (`from_json` on the `meta` column for file counts, `count_if`) has not been run against a live warehouse.
- **Me** view (`Mine`): a sentence summary with Questions/Conversations (with deltas), Active days and Current streak (computed client-side from `per_day`); activity chart; "Your go-to assistants" with an **Ask** button (needs the `agents`, `onOpen`, `onResume` props from `page.tsx`; an assistant you lost access to shows "No access"); recent conversations (`api.chats("")`); a weekday x hour heatmap in the viewer's time zone; and "Your files" (sent and received, with Download only when the agent has `output_volume`, via `downloadUrl`). Extras come from `GET /api/dashboard/me/insights` (`dashboard.insights`: UTC hour buckets plus files parsed from message `meta`; received files that echo an upload in the same conversation, which Agent Bricks does, are dropped). ### 11. Portal Deployer (`deployer/`, `.github/workflows/`, `ui/app/*.deployer.tsx`, `ui/components/deployer/`)
A separate Databricks App in **our** workspace that deploys the portal into client workspaces. `deployer/README.md` has the setup.
- **Stores nothing itself.** Clients are GitHub Environments `client-<slug>` (settings as variables, the client's service principal secret as an environment secret, sealed with PyNaCl in `ghub.seal` before it leaves the process and never returned). Versions are GitHub Releases (`release.yml` publishes a `vX.Y.Z` tag only after `ci.yml` passes). What happened is an append-only Delta record (`registry.py`: `deployments`, one row per step, newest row per `deploy_id` = its state; `health`) in `REGISTRY_SCHEMA`.
- **Deploy** = `deploy.yml` (workflow_dispatch, runs in the client's environment, one per client at a time) running `deployer/deploy.py`: sign in as the client SP (M2M OAuth), ensure app + ACTIVE compute, access (users group CAN_USE on the app, warehouse CAN_USE + history schema grants for the app's SP; refusals are warnings), `git archive <tag>` staged with a `VERSION` file and the client's `env:` in app.yaml (`workspace.client_yaml`), upload over the Workspace API (`workspace.upload`: clear the folder, mkdirs, `workspace/import` format AUTO, 4 at a time with back-off on 429; seen live: 103 files in 7 s, identical to `import-dir`; the CLI is not used because it always asks for `all-apis`) to `/Workspace/Users/<sp>/agent-portal/<app>/<version>` (the folder name **is** the version, so the live version is read from the app's active deployment), scopes from `update-scopes.json` (restart only if changed), deploy, verify (`workspace.check`). Any failure after the live app starts changing puts the previous version back from its folder (`roll_back`, its own `auto_rollback` record) and verifies it.
- **Sign-in scopes** (`common.m2m_token`): asks for `all-apis`; if the client's secret was created with only specific scopes, asks for `common.SCOPES` (`apps, workspace, sql, unity-catalog, model-serving, supervisor-agents, secrets, access-management`; permission changes are `access-management`, per Databricks' scope reference). Checked live on an AWS workspace with a secret holding just those eight.
- **Health** (`health.yml`/`health.py`, on demand and after every deploy): Databricks' view of the app, then the portal's `/api/health` (now returns `version`) and, if the SP counts as a portal admin, error counts from `/api/admin/agent-health` and `/api/admin/logs`. Statuses healthy / degraded / down / unverified (the app refused the SP's token; unconfirmed whether Apps accepts it).
- **Deployer app** (`deployer/app.py`, `clients.py`): only `DEPLOYER_GROUP` (default `admins`) members, read with the caller's own token; the actor recorded is from the token, never the request. A deploy is recorded `requested` before GitHub is asked; `clients.status` reconciles with the GitHub run (`run-name` carries the id) so a job that died or never started is recorded as failed. Workflow inputs reach scripts only as env vars and are validated (`common.*_RE`).
- **UI**: same `ui/` project, built with `npm run build:deployer` (`next.config.mjs` switches `pageExtensions` to `deployer.tsx` and `distDir` to `out-deployer`; copy to `deployer/web/`, committed). It reuses the portal's components (`Card`, `Chips`, `Find`, `Tag`, `Pre` from `Ops.tsx`, `Kpi` from `Dashboard.tsx`, `Select`/`Pager` from `bits.tsx`) so both products look identical; `OpenRow` in `deployer/parts.tsx` is `Row` with its detail outside the button (details hold links). Phones get stacked cards instead of the clients table.
- **Setup page** (`readiness.py`, `GET /api/setup`): read-only checks of everything the deployer needs (GitHub token, Administration permission via `actions/permissions`, workflows, the four `HOME_*`/`REGISTRY_SCHEMA` variables, `HOME_CLIENT_SECRET`, a published release, the registry), each with its fix; the sidebar badge and the Clients next-step banner use the same count. Learnt live: a fine-grained token needs **Administration: write** to create an environment; an app deployed before its secret resource was added runs without it (redeploy); an OAuth *app connection* id authenticates but gets 403 "Scopes 'all-apis' are not assigned" (not a service principal).
- **Client branding** (logo, portal name, one brand colour): set on the client's Settings tab or in Add client (`Branding.tsx`, live light/dark preview), kept as the client's GitHub variables `BRAND_NAME`, `BRAND_COLOR`, `BRAND_LOGO` (a PNG data URL; the browser fits every upload, SVG included, into 256 px PNG under 40 KB, so no SVG script ever reaches the portal; `common.check_logo` re-checks magic, size and 512 px). The deploy writes the logo to `branding/logo.png` in the release (gitignored) and `PORTAL_BRAND_NAME`/`PORTAL_BRAND_COLOR` (JSON-quoted) into app.yaml. The portal returns `brand` in `/api/session`, serves `/api/brand/logo`, and `ui/lib/brand.ts` turns the one colour into every brand token for light and dark (contrast-checked: 4.5:1 button text, 3:1 links), injected as a `html:root` stylesheet and cached for the pre-paint boot script so a branded portal never flashes teal. The deployer preview uses the same `palette()`. "Apply now" after saving redeploys the live version.
- **Assistants and an empty portal** (learnt treating our own workspace as a client): the portal lists only assistants shared with its own identity, and workspace admins get no automatic access to agents, so a fresh install is empty. Each deploy (`workspace.share_agents`, client setting `SHARE_AGENTS`, default on) gives the app's service principal CAN_MANAGE on every assistant the installer can see (endpoint, plus the Agent Bricks list via the `agent_id` tag) and names the ones it could not. The portal's `/api/health` reports `assistants` (count visible to its identity, cached 60 s); the health check marks 0 as degraded with the app's id to share them with, and the client Overview shows it, and any deploy warnings, as the next step.
- **Catalog check before deploy** (`clients.catalog_access`): the connection check marks each catalog ready / needs_grant. Learnt live: a catalog owned by the `_workspace_admins…` group lists no effective privileges for an admin service principal yet lets it create schemas; one with only USE_CATALOG does not. The Options step sorts ready catalogs first and shows the exact GRANT for one that is not.
- **MCP catalog per client** (`workspace.mcp_ref`/`stage_mcps`, `deploy.ship_mcps`, `ghub.mcp_versions`/`mcp_tools`, UI `Tools.tsx`): the MCP repo (`MCP_REPO`, default `manikantakarri-oss/mcps`) publishes versions from tags (its `catalog.yml` validates every `mcp.yaml`/`app.yaml` first). Each client has `MCP_CATALOG` ("" = newest tag, else a pinned tag) and `MCP_ALLOW` ("" = all tools, `none`, or a comma list). The deploy resolves the ref to a commit, unpacks only the client's MCPs (never `_template`, tests or caches; paths checked) into `mcp_catalog/` in the release with `CATALOG.json`, and records it. The portal (`mcps.LOCAL`) reads that folder instead of GitHub when present, so a client only has its own tools, at a pinned version, with no GitHub access or token in its workspace, and a rollback restores the old catalog. Older releases and checkouts still read the repo.
- **Removing a client** (`clients.uninstall`, `POST /api/clients/{env}/uninstall`, `uninstall.py`, action `uninstall` in `deploy.yml`): a job signs in as the client SP and removes the portal app, the tool apps it installed (code under `/Workspace/Shared/agent-portal-mcps/`), the `agent-portal` secret scope, the release and tools folders, and, only when ticked, the `portal_logs`/`portal_chats`/`portal_events` tables. Assistants are kept (they are the client's, and nothing marks which were built in the portal). If another portal app runs in the same workspace, shared tools, keys and the tools folder are kept. While it runs the client has `REMOVING=<id>` and deploys are refused; the GitHub environment is deleted only when the job succeeded (`status` -> `_finish_removal`, also on the next client list), a failure clears the flag so it can be retried. `DELETE /api/clients/{env}` ("Only remove it here") forgets the client without touching their workspace, for one that is gone or locks the installer out. **Unconfirmed live:** the whole removal job.
- **Fleet rollout** (`clients.rollout`, `POST /api/rollouts`, `rollout.yml`, UI `Rollout.tsx` from a release): one canary client, then the rest `parallel` (1/3/5/10) at a time via a GitHub matrix with `fail-fast` (stops at the first failure; deploy.py already rolls the failed client back). Every client's deploy is recorded first (`detail.rollout_id`, `wave`); ineligible clients (already on it, deploying, incomplete) are skipped with the reason; clients whose turn never came are recorded as "rollout stopped" (`status` checks the rollout run). The deploy steps live in the reusable `deploy-one.yml` (with the per-client concurrency group; it must not also be on the caller), used by `deploy.yml` and `rollout.yml`.
- **Speed at 100 clients**: the Clients page loads the record queries and every client's GitHub settings in parallel over pooled connections (`common._http`, `ghub._http`), GitHub reads are conditional (ETag, a 304 is free of the rate limit, any write clears them), and startup probes the tables with one query. Measured live: 13 s → 1.1 s.
- UI shape: each page leads with one next step (`NextStep`); Add client is a 3-step flow (Client, Connect with a copyable message for the client's admin and a required connection check, Review with history on/off + catalog and "Add and deploy"); the client page has Overview / History / Settings tabs and a Deploy dialog (`Dialog`) that never preselects an older version.
- Tests: `python deployer/test_deployer.py` (offline). **Unconfirmed, never run live:** the whole deploy against a client workspace.

### 12. Assistant designer (beta) (`designer.py`, `designer_prompt.md`, `ui/components/Designer.tsx`)
**Describe it in your own words**: an admin-only option at the top of the Build type picker (a "Not sure which to choose? Just describe it." panel above the three kinds, because it is a *way of choosing*, not a fourth kind). On unless an operator sets `PORTAL_DESIGNER=off`; when on but this admin has no usable chat model it is shown disabled with the reason, never hidden (hiding it is what made it "missing"). The UI asks `GET /api/admin/designer/status`. A short interview (4-6 questions, clickable options, plain English for non-technical admins) fills in a **draft**, shown beside the chat; **Approve and build** creates it; the new assistant is then **tested**. Inspired by Mediamint's Mia Studio (pre-interview, discovery, spec gate, code-or-llm, eval), rewritten for Databricks; none of its runtime is used.
- **The model never builds anything.** It talks through function calling to a Databricks chat model the admin chooses on screen (see "Which AI model" below; by default Claude Sonnet), under the **admin's own token**. It has read-only lookups (catalogs, schemas, tables, a table's columns, folders, functions, warehouses, existing Genie/document assistants, the ready-made MCP tool list, teams and people; each reuses `builder.sources`/`mcps.listing`/`access.principals`) and three control tools: `update_draft`, `ask` (one question, optional options), `propose` (summary; **refused with reasons** while anything is missing or does not exist). Several lookups in one reply run in parallel.
- **The draft has the shape the three builders already take** (`kind` = `supervisor` | `genie` | `knowledge`, plus their fields, `access`, `access_decided`, `gaps`). `designer.check` runs the builders' own `clean`/`clean_spec` plus a few floors (a description, real instructions, at least one tool / two example questions, who may use it answered); `designer.verify` confirms everything it names exists (tables, folders, functions, spaces, assistants, catalog tool, warehouse) as the admin. Both run on every `propose` **and again on `POST /api/admin/designer/build`**, because the draft round-trips through the browser. Build then calls `_create_supervisor` / `_create_genie` / `_create_knowledge` in `app.py`, the same code the wizards' routes use (`via: "designer"` on the audit record), so all-or-nothing create, identity fallback, MCP deploy-and-attach, provisioning and sharing are unchanged. Catalog tools not yet running are installed in the background and attached later (the existing safety net), and the finish screen says so.
- **Stores nothing, keeps no session.** Serving endpoints are stateless, so the browser holds the transcript and the draft and sends both each turn (also kept in `sessionStorage` to survive a refresh). Lookups happen inside one request and are not carried over, so the draft, not the transcript, is the memory. **What the admin types is never logged or recorded** (same rule as the audit log); only the finished assistant is, by the create routes. A transcript is capped at 40 messages; a single message has no length limit.
- **It reads tools before relying on them, and says what is missing.** `describe_ready_made_tool` returns, for one catalog tool, each ability's description, parameters and docstring, what it needs (connection settings, folder access `read`/`write`) and whether it is `connected_here`. The parameters come from `mcps.source_summary`, which parses the tool's `server.py` with `ast` as text and **never runs it**. `find_ready_made_tools` lists tools that are not connected too (`usable_here: false` with the reason; `verify` still refuses to build with one). The draft carries `coverage`: one row per specific thing the admin asked for (`covered` / `partly` / `missing`, which tool covers it, a note), and `check` refuses to propose a tool-based assistant until it exists. The prompt forbids instructions or tool descriptions that promise a `partly`/`missing` need, and tells the model to offer concrete options (never an open "how should I proceed?"). The side panel shows the list in words; the test planner writes a question for each `partly` need. Found live: with the real GAM tool it correctly reports that Excel rate cards are not read (its `get_rate_card` uses prices from the network's line items; folder access is `write` only) and that there is no country filter.
- **Tools already installed are looked at before anything new is proposed.** The ready-made list is only the git catalog, so a tool running in the workspace with no catalog entry (one this designer built earlier, or one deployed by hand) used to be invisible and the designer offered to build it again (seen live: `mcp-rate-card-reader` existed, was running, and the designer asked where the files were and offered to write one). `find_installed_tools` lists tool apps (`mcps.installed`: named `mcp-*` or marked with `mcps.GEN_MARK`, not in the catalog; ordinary apps such as the portal itself are left out) and `describe_installed_tool` reads one (`mcps.installed_detail`): its card (`mcp.yaml`), each ability's parameters and docstring (`mcps.parse_source`, `ast` on the **source kept in `/Workspace/Shared/agent-portal-mcps/<folder>`**, read through `workspace/export` with `format=AUTO`, never run), and the folders it was built for (the `_READ_FOLDERS` / `_WRITE_FOLDERS` constants the assembler writes). A tool whose source is not kept reports `abilities_known: false`, and the prompt makes the designer record what depends on it as `partly` (the tests will try it) instead of pretending. It is attached as `{type:"app", ref:<name>}` with no `mcp` key, and `designer.verify` checks that every such app exists and is **running** before an assistant is built around it (one `GET /api/2.0/apps`). Verified live: the same request now says "a GAM planner and a rate card reader already exist", credits `mcp-rate-card-reader` in the coverage list, and attaches both; it also read from the tool's own source that rate cards must sit in a `rate_cards` sub-folder. A tool can only reach the folders it was built for; the folder grants made at its install still stand, and the portal does not top them up for an installed tool (it does for catalog tools).
- **What exists is put in front of the model, not left for it to find (learnt live, 2026-10-08).** The same request, in a fresh conversation each time, found the installed rate-card tool in 9 of 9 runs on Claude Sonnet 5.5 but in **none** on GPT OSS (20B/120B), Llama 4 / 3.3, Qwen or Gemma, which never called the lookup (some answered "Sorry, I did not catch that" or asked generic questions), and Claude Haiku 4.5 looked but did not use it. An admin on such a model was told "I can't yet read uploaded spreadsheets". So `designer._tools_that_exist` builds a compact list (ready-made tools with abilities and whether usable; installed tools with state, abilities and the folders they were built for; cached 60 s per token, degrades to "use find_*" if the workspace cannot be listed) and `_system` puts it in the instructions on **every** turn, ahead of the draft, with the rule that it is newer than anything said earlier in the conversation. Result: all three Claude models attach the existing reader; GPT OSS, Llama and Gemma still do not engage (a model that will not use tools cannot do this job; no prompt fixes that). `turn` therefore returns `warning` (`NO_LOOK`) when a non-Claude model answered without looking at anything; the screen shows it once per model with a "Choose a model" shortcut, and the picker's caution for untested models says most non-Claude models skipped the look-up in our tests. Do not claim a model works because it answered: check what it looked at. `installed_detail(name, tok, found)` takes the entry already read so building the list does not re-list apps once per tool.
- **A half-finished interview is kept for an hour, and says so.** It is saved in `sessionStorage` so a refresh does not lose it, which also meant an old conversation (with an old assistant claim in it) could be picked up again without any sign. It now expires after 60 minutes (`KEEP_MS`) and, when picked up, the screen says "We picked up the conversation you started earlier" with Start over. A stale claim in the transcript did not fool Claude (4 of 4 runs re-checked), but the model's earlier text is no longer allowed to outweigh the list above.
- **Gaps are said, not faked, and some can be filled with a new tool.** Anything with no tool goes into `coverage` / `gaps` and the summary ("Not included"). A folder tool is described as reading files, but reading a given type (Excel) is **unconfirmed**, so the model records it `partly` and the tests try it. For a missing need that can really be built, the designer may propose a **new tool** (see below) after asking the admin a clear yes/no.
- **New tools (`forge.py`, `designer_code_prompt.md`)**: `design_new_tool` proposes a **SQL function** (`CREATE FUNCTION` only: no OR REPLACE, one statement, no comments, no DML/DDL keywords, one `SELECT` example) or a small **MCP server** (1-4 abilities, 3 tries). A **code model** (chosen under "Fine tune" on the model panel, default = the interview model) writes only the tool functions from the brief; `forge.analyze` rejects the code with plain reasons (retried with them); `forge.assemble` wraps it in a fixed header/footer (FastMCP, `/ping`, `volume_read`/`volume_write`/`volume_list`, `mcp.tool(annotations=...)` per ability) and builds `requirements.txt` from the **imports found** through an allowlist (never a list the model writes), `app.yaml` (settings as `valueFrom`) and `mcp.yaml`. The model only ever sees the draft **without** the code. `update_draft` cannot add new tools (the loop strips them): only `design_new_tool` can.
  - **The static check is a guard rail, not a sandbox** (AST, text only, never imported or run in the portal): no `eval`/`exec`/`open`/`getattr`/dunder tricks, no subprocess/socket/pickle/shutil/pathlib/sys, only `os.environ[...]` for declared settings, imports from a short allowlist, only imports/functions/constants at module level, every ability a typed, documented, non-async function, websites and folders **declared**, saving files or POST/PUT/PATCH/DELETE only from an ability marked `changes_data`. A deny-list can be got round; the real limits are Databricks': the new app runs as its own service principal with **only** the folders its card declares (`mcps.grant_volumes`) and **only connection settings that already exist** in the secret scope (the portal never handles a secret value; `find_connection_settings` lists names only). File access goes through helpers the portal wrote (the app's own identity, Files API, refusing any path outside the declared volumes), so generated code never sees a token.
  - **Review is the gate.** The review screen shows the code, a plain list of what it can reach and a per-tool tick. Approval is the tool's `fingerprint` (sha256 of everything that decides what is created, recomputed server-side, never taken from the browser); `POST /api/admin/designer/tools/create` refuses unless the set of approved fingerprints equals the tools being created, and re-runs `check` + `verify`. Functions are created **in the request as the admin** (Statement Execution API, their own token, no fallback; Databricks decides); a refusal stops everything before any app starts and says what was already made. Apps install in the background through `mcps.install(entry, who, tok, files=...)` (same path as catalog tools, files from memory instead of the tarball) and the UI polls `GET .../tools/status`; when running, `POST .../build` (which now `verify(created=True)`s that functions exist and apps run) attaches them like any tool. Created functions become ordinary tools of the draft client-side so a retry never creates one twice.
  - **A generated tool passes every check and can still fail on the first real file (learnt live, 2026-10-08).** `mcp-media-plan-tool` (`read_adbook`) failed on a real ad book with `'MergedCell' object has no attribute 'column_letter'`: walking a row of a real spreadsheet reaches merged-cell placeholders, which have no `column_letter`. The static check cannot know that, so `forge.analyze` now refuses `.column_letter` outright (use `get_column_letter(cell.column)`) and `designer_code_prompt.md` warns the writer about merged cells, empty rows, header blocks, numbers stored as text and `#REF!`/`#DIV/0!` values. These checks are a guard rail: the only real exercise a tool gets is the **Test stage**, so a test question should make each ability read a realistic file. The live tool was repaired in place (three lines in `/Workspace/Shared/agent-portal-mcps/media-plan-tool/server.py`, redeployed) and then confirmed by asking its assistant to read the real ad book: 5 sheets, 111 line items. To repair a tool like this the same way: back up its `server.py`, reproduce the failure locally on a made-up workbook that has merged cells (`openpyxl` + the file's own `volume_read` replaced by the bytes), fix, re-run, import over the workspace file, `POST /api/2.0/apps/<name>/deployments` with `source_code_path` and `mode: SNAPSHOT`, wait for `SUCCEEDED`.
  - **A new tool is tried on real files before the assistant is built, and repaired if it breaks (`tooltest.py`, UI `designer/ToolCheck.tsx`).** Added after `mcp-media-plan-tool` passed every static check and then crashed on the first real ad book. Once a new tool is running and *before* `POST .../build`, the Create stage opens a "Trying out" screen: `tool-test/plan` reads the deployed tool back from the workspace (`forge.item_from_workspace`: only an app marked with `GEN_MARK` can be read, so only the designer's own tools are tested or repaired), lists the folders it declared (`tooltest.facts_for`, as the admin, one level down), asks the chat model for calls from the tool's real input schemas (`tools/list`) and the file names it finds, plus one deliberately wrong call per ability (a clean refusal is expected, never a crash); `tool-test/run` calls one ability over MCP streamable HTTP under the admin's token (`tooltest.Client`: `initialize`, `notifications/initialized`, `tools/list`, `tools/call`; the reply is one server-sent event or plain JSON; no `Authorization` header when there is no token); the screen shows one row per try.
    - **Only read-only abilities are run.** The tool's own `readOnlyHint` decides (the assembler sets it from `changes_data`), not anything in the request; the run route re-reads it and refuses others with 400, and the plan lists them as "not tried: it saves or changes something, so it is never run without you".
    - **Judging is by rule, deliberately (learnt live).** On the wire a crash is `isError` with the exception text (**fail**), a handled refusal is `ok: false` (a wrongly refused realistic call is **fail**; a clean refusal of the deliberately bad call is **pass**), and a call whose arguments do not fit the schema is rejected before the tool runs with "validation error" (**unchecked**: a bad test says nothing about the tool). A working answer is questioned only if it holds nothing (**look**, `substance`), and input that was meant to be refused but was accepted is also only **look**. An earlier version asked a model whether a working answer "looked right": it produced false alarms (it called an answer "truncated" because *we* had cut the text it was shown, and second-guessed answers that were fine), and since a fail sends the code model off to rewrite the tool, a false alarm is not harmless. Say "it runs and answers", never "it is correct".
    - **Repair is propose, read, approve, deploy, retest.** `tool-test/fix` has the code model (`propose_fix`, `FIX_PROMPT` on top of `designer_code_prompt.md`) return the whole corrected code and a one-line plain explanation; it must pass `forge.analyze` (up to 3 tries, each told what was wrong) and may reply `NO CHANGE NEEDED:` when the test was at fault. The screen shows the explanation and a +/- diff (`forge.code_diff`); the admin ticks that they read it; `tool-test/apply` re-reads the deployed tool, re-checks the code as if new, requires `approved` to equal the fingerprint of exactly that code, and redeploys through `forge.install_app`. `tool-test/ready` then answers "has it gone live": the app keeps serving its **old** version and reports RUNNING while a new deployment is going in, so "running" is the wrong test; ready means nothing is `pending_deployment` and the `active_deployment` succeeded with a `create_time` newer than the moment of applying (`tooltest.deployed_since`). The same plan is then run again; at most three repairs, then it says a person must look. Audit: `fixed_tool` (the explanation, never the code).
    - **Verified live (2026-10-08)**: the client against the deployed tool (initialize, list, call, a crash, a refusal, a schema rejection), `facts_for` on the real folders, the plan and runs on `mcp-media-plan-tool` (false alarms gone after dropping the model judge), and the real code model repairing the real original bug in 23 s (a 29-line diff that passes the checks and reads a merged-cell workbook), plus a real FastMCP server in `test_tooltest.py` taken through find-the-bug, repair, restart, retest. **Unconfirmed**: calling a tool's app with the signed-in user's token **inside a deployed portal** (the Apps proxy accepted the local CLI OAuth token; whether the token a deployed portal receives carries the scope is untested). When the tool cannot be reached the screen says so and offers "Skip the check and continue".
    - Not built: a standalone "check this tool" page for tools that already exist (the routes work for any designer-made tool); running abilities that change things (never automatic).
  - **It never overwrites**: a function or app that exists is refused, except an app whose description starts with `forge.GEN_MARK` (this designer's own earlier attempt); a slug in the catalog is refused. The source lives in `/Workspace/Shared/agent-portal-mcps/<slug>` (Databricks; the portal still stores nothing) and the app is `mcp-<slug>`; copy the folder into the catalog repo to keep it. Audit: `created_tool` (kind, name, fingerprint prefix; never the code).
  - **People also need EXECUTE on a created function** (the portal does not grant it, same as `SELECT` for Genie).
  - **Verified live (2026-10-08)**: the code model wrote a clean 217-line Excel rate-card reader for the real media-planner request and it passed the checks first time; `run_sql` (SELECT and a failing statement, Databricks' own error text), `name_problems` (free names, catalog/app collisions) and the Files API directory listing shape (`contents[].name/is_directory`) against the live workspace; the assembled server loads in the **real FastMCP** (tools listed with the right read-only flags, folder guard refuses other folders). **Not run live**: creating a function, installing a generated app, a Supervisor accepting it, the review/create UI. Files may sit in a sub-folder (the volume root here holds only `uploads`, `output`, ...), so the interview asks which.
- **Evals** (`POST /api/admin/designer/test-plan`, `.../test-run`, `GET .../assistant-state`): the model writes 6 questions from the draft (typical, one vague, one out-of-scope that should be declined) with a plain-English expectation; once the new assistant's endpoint is ready (the UI polls, up to 25 minutes) each question is asked **as the admin through `chat.ask`** (not `/api/chat`, so it is not saved to chat history, dashboards or Monitoring) and a **different model** (chosen automatically, or under "Fine tune") marks the answer pass / fail / ungraded. A failed answer or a failed tool is a *result*, not an error; an unclear verdict is `ungraded`, never a pass. The UI says plainly it checks that answers are sensible, **not that numbers are right**. The question, expectation and answer are sent to the judge as JSON data, never as instructions.
- **Learnt live (2026-10-08, Azure, `databrickspoc`)**: Claude on Databricks **rejects `temperature`**; a reply's `content` is a string, null, or a list of blocks that can include `reasoning` blocks with a signature, and the assistant message must be **echoed back unchanged** with its tool results (the tests pin this); `databricks-gpt-oss-120b` works as the judge. Interviews take 5-25 s per turn (lookups dominate).
- **Verified live**: model tool-calling round trip, two full scripted interviews (a data assistant over `samples.bakehouse`; an Ad Manager tool assistant that correctly reported Slack as missing), `verify`, test-plan, the judge, `test-run` against an existing assistant, all through the real HTTP routes. **Not run live**: `POST .../build` (the creators it calls are unchanged and covered by their own tests; the route is tested with a fake creator) and the browser UI (type-checked and built, never driven).
- **Which AI model (`designer_models.py`, UI `designer/ModelPicker.tsx`, `lib/designerModels.ts`)**: chosen **on screen**, per admin, remembered in their browser (`localStorage`, a per-person convenience; a saved choice no longer on offer is dropped). Three jobs, one real choice: *chat* (the interview; the only choice most people make), *code* (writes new tools; "same as chat" unless set), *judge* (marks test answers; defaults to a **different** model than chat, computed against the model actually *chosen*, not the default one: a test caught this being wrong). What is offered is read from `GET /api/2.0/serving-endpoints` **under the admin's own token**: chat-task, READY, and the admin holds CAN_QUERY or CAN_MANAGE (so a model they cannot call is never shown), cached 60 s per token. Best first: newest Claude Sonnet, other Claude, then the rest; only Claude is marked "Recommended" (the interview needs function calling and long tool use, which is what they are documented for; only Claude Sonnet 5.5 and, for judging, GPT OSS 120B have actually been run here), others say "Not tested for this" rather than guessing. A choice sent from the browser is validated (name pattern, and in the offered list when the list can be read) so a stale or typed name gets a plain 400; the call still runs as the admin, so Databricks enforces access whatever is sent. `PORTAL_BUILDER_MODEL`, `_CODE_MODEL` and `_JUDGE_MODEL` are now only **optional pins** for defaults (a pinned model not in the list is still offered, marked "Set up by your administrator"); `app.yaml` sets none. With no pin and no models available, the screen says how to fix it (ask for Can Query on a chat model).
  - **A retired model is listed as ready (learnt live, 2026-10-08).** `databricks-claude-sonnet-4` showed `READY`, `CAN_MANAGE` and normal fields while every call returned 400 "This endpoint ... is deprecated"; nothing in the listing marks it. An admin who picked it got "The model could not answer". So retirement is **learnt from the refused call**: `designer._complete` raises `ModelRetired` (400/404/410 whose message says deprecated/retired/decommissioned/no longer available), `designer._ask` (which every model call goes through) marks it retired (`dm.mark_retired`, process memory, hidden from the list), moves every job that used it to the next best (`dm.fallback`), retries, and the turn returns `notice` ("Claude Sonnet 4 has been retired by Databricks, so Claude Sonnet 5.5 was used instead."); at most three swaps, then a plain message. A *saved* choice of a retired model is replaced the same way (`resolve(..., notes)`). The screen shows the notice, reloads the list and forgets the stale choice. Do not add a hard-coded list of retired models: it would go stale.
  - **The listing also reports `capabilities.function_calling` and the real price** (`foundation_model.input_price` / `price`, DBUs per 1M tokens), so both are read, not guessed from the name. A model with `function_calling: false` (Llama 3.1 8B) cannot run the interview (it is shown, greyed out, "No tool use"; the API refuses it for chat with a 400) but may still write code or mark answers. The cost word ("Low / Moderate / Higher cost") comes from the output price (thresholds 40 and 200 DBUs per 1M tokens) and the picker shows "28.6 in, 142.9 out per 1M tokens (DBUs)". Prices are DBUs, not dollars; the Insights page shows real spend by model, from billing, which lags by about three hours.
  - Learnt by probing all 24 listed chat models with a one-word request: 23 answered, 1 was retired; Llama 3.1 8B answered but cannot use tools.
- **The screen (designed for non-technical admins; checked in a real browser at desktop and phone width)**: four stages always shown (**Describe, Review, Create, Test**; only the current one is named on a phone). Describe is the interview beside a summary whose **checklist is in plain words** (`designer.progress`: "What it is for", "What it uses", "Who can use it", ...; the model-facing `check` strings, which say things like "record it in coverage", are never shown) with a progress bar and **the main button directly under it**, so it is on screen without scrolling (an earlier layout hid it below the fold). The conversation shows "Looked at your tables and your SQL warehouses" under replies, starter suggestions on the first turn, quick-answer buttons, and when ready an in-chat "Review and build / Change something". Errors from building sit beside the button (the chat's retry would re-ask the model). Review shows what a new tool can reach in words first, the code behind a labelled button (with line count and Copy), one tick per tool, and an action bar in the page's flow. Create lists every step with its state and, on failure, which step, with Try again (functions already made become ordinary tools so a retry never repeats them) and Back. Learnt from screenshots: **never fix anything to the bottom of the screen on a phone** (it covered the text box), **never link to `#something`** (this app navigates by the URL hash; use scroll-into-view), and **do not autofocus the text box on touch devices** (opens the keyboard and scrolls). The test suite does not cover the UI; it was driven with puppeteer against the real portal with the create/build/test calls faked.

## Conventions

- Python 3, `from __future__ import annotations`, httpx for all HTTP, route handlers stay thin and delegate to modules. Module docstrings explain *why* (verified Databricks behaviour); keep that style and record new findings there rather than in commit messages.
- Calls to Databricks go through `dbx.call` and raise `DbxError(message, status)`; routes mirror the status. Use the quiet option for expected failures so they don't pollute the Problems log.
- All SQL uses bound parameters; identifiers (table names) are validated against `_NAME_RE` before use.
- The UI talks to the backend only through the typed wrapper in `ui/lib/api.ts`; add new endpoints there. Copy is written for non-technical readers: plain English, no Databricks jargon in user-facing text.
- Next.js is pinned exactly (`output: "export"`, no server features such as API routes, SSR or middleware).
- Don't claim Supervisor Agent, Genie or Knowledge Assistant builder behaviour is verified live; shapes come from the API references and the Databricks create screen (see README).

## Known gaps

- Data-backed agents also need Unity Catalog grants (`USE CATALOG`/`USE SCHEMA`/`SELECT`) for the end user; the portal reports the failure but cannot fix it.
- Only Supervisor Agents, Genie spaces and Knowledge Assistants can be built; custom agents, MCP servers and UC connections are created in Databricks and only *attached* here. Knowledge Assistant sources other than volume folders (search index, table of files) are not offered.
- Group membership edits replace the whole list.
- Dashboards need saved chat history and only cover chats since it was turned on; per-person cost is an allocation estimate.
- Uploads are named by path in the message, not via Agent Bricks' own "Conversation Files" (no public API).
- Some README sections predate chat history and the activity/problem logs (e.g. "No chat history" under Known V1 gaps); trust this file and the code.
